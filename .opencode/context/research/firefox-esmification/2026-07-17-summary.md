# ESMification: Firefox JSM-to-ESM Migration — Phase 1

**Source:** Google Doc (Mozilla internal → public)  
**Topic:** Converting Firefox's legacy JSM module system to standard ECMAScript Modules (ESM)

## Overview

Phase 1 focuses on converting existing JSM files to ESM with minimal changes, keeping behavior identical as much as possible. The migration is designed to be incremental — each module can be converted independently of its consumers.

## Key Concepts

### JSM (Legacy)
- Mozilla-specific module system
- `.jsm` file extension
- `EXPORTED_SYMBOLS` global variable defines exports
- `ChromeUtils.import()` API for consumers
- "Lazy getters" via `XPCOMUtils.defineLazyModuleGetters`
- Per-process singleton, shared among all consumers

### System ESM (New)
- Standard ECMAScript Module syntax
- `.sys.mjs` file extension (distinct from non-system `.mjs`)
- `export` / `import` syntax
- `ChromeUtils.importESModule()` for non-ESM consumers
- Static `import` declarations supported inside system ESMs
- Still a per-process singleton (same shared global as JSM)
- Synchronous loading (unlike web ESM)

### What Stays the Same
- Per-process singleton behavior
- JSM and ESM files can be mixed in the same import graph
- Consumer interface (same exported symbols)
- Lazy getters (now via `ChromeUtils.defineESModuleGetters`)
- URI scheme (`chrome://` and `resource://`)
- `moz.build` and `jar.mn` definitions (just change extension)

## New APIs

| API | Purpose | Replaces |
|-----|---------|----------|
| `ChromeUtils.importESModule()` | Sync load ESM, returns namespace | `ChromeUtils.import()` |
| `ChromeUtils.defineESModuleGetters()` | Define lazy getters on object | `XPCOMUtils.defineLazyModuleGetters()` |
| `Cu.isESModuleLoaded()` | Check if ESM loaded | `Cu.isModuleLoaded()` |
| `Cu.loadedESModules()` | List loaded ESMs | `Cu.loadedModules()` |
| `Cu.isJSModuleLoaded()` | Check if JSM loaded (new) | N/A — purely for JSMs |
| `Cu.loadedJSModules()` | List loaded JSMs (new) | N/A — purely for JSMs |
| `esModuleURI` key | Window/Process actor registration | `moduleURI` key |
| `esModule` key | `components.conf` entry | `jsm` key |

## What Changes with System ESM

### 1. Static Import
Inside system ESM, other system ESMs can be imported with static `import` declarations — handled at compile time. Supports relative URIs.

### 2. Always Strict Mode
ESM is always strict mode — no `"use strict"` needed.
- No `with` statement
- No legacy octal
- Reserved words (`let`, `static`, `implements`, etc.) cannot be variable names
- No duplicate parameter names

### 3. No Per-JSM Global `this` Object
JSM had per-module `this` used for:
- **Defining global variables:** `this.foo = ...` → now use `var` / `let` / `const` / `function` / `class`
- **Exporting lexical vars to `Cu.import`:** `this.Foo = Foo` hack no longer needed (bug 1768060 fixed this)
- **Defining lazy getters:** now must use a plain `lazy` object instead of `this`

## Restrictions
- Dynamic `import()` — not available (fixed in bug 1875836)
- Top-level `await` — not available (loader is synchronous)
- Workaround for dynamic import: use `ChromeUtils.importESModule()` instead

## Compatibility Layer

### Auto-Redirect: `ChromeUtils.import("foo.jsm")` → ESM
When `ChromeUtils.import` is called with a `.jsm` / `.js` / `.jsm.js` URI:
1. Check cache for redirect
2. Try loading the file as-is (JSM)
3. If JSM not found, try ESM with `.sys.mjs` extension
4. Cache the redirect for future calls

Conditions for redirect to work:
- Same set of exported symbols
- Same behavior of exported symbols
- Same URI except extension (`.jsm` → `.sys.mjs`)

### Migration Without Consumer Changes
A module can be converted to ESM without touching any of its consumers. The redirect layer makes this possible, including for out-of-tree code (privileged extensions, AutoConfig files).

### When Redirect Doesn't Work
If the old extension doesn't match `.jsm`/`.js`/`.jsm.js`, or other issues:
- Move implementation to new ESM file
- Make the old JSM a thin wrapper that `ChromeUtils.importESModule()` the new ESM

## Migration Walkthrough

### Automated via `./mach esmify`

```bash
$ ./mach configure
$ ./mach esmify [options] PATH_TO_JSM_OR_DIRECTORY
```

**Example 1: Full tree conversion**
```bash
$ ./mach esmify --convert browser/components/pagedata
$ ./mach esmify --imports . --prefix=browser/components/pagedata
```

**Example 2: Directory-local conversion**
```bash
$ ./mach esmify browser/components/pagedata
```

### Step 1: Convert JSM to ESM (`--convert`)
- a. Rename `.jsm` → `.sys.mjs`
- b. Update `moz.build` references
- c. Replace `EXPORTED_SYMBOLS` with `export` declarations
- d. Rewrite `ChromeUtils.importESModule` → static `import` (inside ESM files)

### Step 2: Rewrite Consumers (`--imports`)
- a. Replace `ChromeUtils.import` → `ChromeUtils.importESModule` (in JSM/ESM consumers)
- b. Replace `ChromeUtils.import` → static `import` (inside ESM files)
- c. Replace `XPCOMUtils.defineLazyModuleGetters` → `ChromeUtils.defineESModuleGetters`
- d. Rewrite `components.conf` (`jsm` → `esModule`)
- e. Rewrite `ChromeUtils.registerWindowActor` (`moduleURI` → `esModuleURI`)
- f. Rewrite `ChromeUtils.registerProcessActor` (`moduleURI` → `esModuleURI`)
- g. (Manual) Rewrite `Cu.isModuleLoaded` → `Cu.isESModuleLoaded`
- h. (Manual) Rewrite `Cu.loadedModules` → `Cu.loadedESModules`

## Known Edge Cases

| Issue | Cause | Solution |
|-------|-------|----------|
| Empty line insertion | `recast` module limitation | Manually revert whitespace changes |
| JSM also loaded as CommonJS | Dual-format files | Duplicate file or rewrite CommonJS consumers |
| JSM loaded from DevTools CommonJS | DevTools loader | Rewrite require to use `.sys.mjs` |
| JSM also loaded as worker script | `importScripts` doesn't work with modules | Wait for module support in workers |
| Filename collision | `.jsm` + `.js` in same dir | Rename one file first |
| Strict mode incompatibility | Legacy JS patterns | Fix code for strict mode, re-run eslint |
| Auto-generated files | Vendored/codegen | Manual migration needed |
| Performance test monitoring | Startup monitoring tests | Update URIs in test files |

## Relevance to This Project

This Firefox theme project uses **UserChrome.js** scripts (`.uc.js`, `.uc.mjs` files) loaded via `fx-autoconfig`. While these are not the same as system modules, understanding Firefox's ESMification is relevant because:

1. The `second_sidebar.uc.mjs` entry point already uses ES module syntax — it mirrors the system ESM pattern
2. Firefox's internal APIs referenced by userChrome.js scripts may transition to ESM, changing how they're imported
3. The `lazy` object convention for getters is used in several scripts
4. The compatibility layer approach (thin wrappers) is a pattern applicable to maintaining backward compat in userChrome.js scripts across Firefox versions

## Terminology

| Term | Definition |
|------|------------|
| System module | Code loaded by mozJSModuleLoader (formerly "JSM") |
| ESM / ES Module | ECMAScript Module (standard) |
| System ESM | System module written as ESM (`.sys.mjs`) |
| JSM | System module in legacy script syntax (`.jsm` or `.js`) |
| Non-system ESM | Standard ESM not loaded as system ESM |
| Shared global | Global object shared by all system modules (`globalThis`) |
| Per-JSM global | Object holding JSM's global variables (does not exist for ESM) |
